Infrastructure Copilot: Product Engineering Constitution

1. Business Perspective
Infrastructure Copilot is not a chatbot. It is an enterprise AIOps and infrastructure intelligence platform.
The product must help enterprises reduce operational pain in areas where they already spend money:

Incident triage
Major incident management
Change impact analysis
Infrastructure health visibility
Runbook and SOP retrieval
RCA/PIR generation
Alert correlation
Cloud cost and reliability recommendations
DevOps/SRE workflow assistance
ITSM integration

Microsoft’s Azure guidance separates SaaS as a business model from multitenancy as an architecture concept, which matters because we are not merely building a hosted app. We are building a vendor-operated product where multiple enterprise customers consume the same platform while requiring strict customer isolation. [learn.microsoft.com], [learn.microsoft.com]
The enterprise buyer will not pay because the AI “answers questions.” They will pay if it improves:

Mean time to acknowledge
Mean time to resolve
Change failure analysis
SLA compliance
Incident communication quality
RCA quality
Engineer productivity
Audit readiness
Operational governance

My challenge to your assumption: Do not start with “AI features.” Start with painful enterprise workflows. AI is the accelerator, not the product. If the workflow is not valuable without AI, adding AI just creates an expensive hallucination machine wearing a blazer.

Microsoft’s RAG architecture guidance describes a pattern where the user query goes to an intelligent application, then an orchestrator determines the search, retrieves top results from Azure AI Search, packages results with the prompt, sends it to the language model, and returns the response. It also describes the grounding data pipeline: ingest documents, chunk them, enrich metadata, embed chunks, and persist them in a search index. [learn.microsoft.com]
For secure multitenant RAG, Microsoft guidance explicitly highlights that tenants and users must only incorporate grounding data they are authorized to access. That must become a non-negotiable architectural rule for Infrastructure Copilot. [learn.microsoft.com]

Recommendation: Start with a modular monolith using clean architecture, domain modules, strict interfaces, and event-driven boundaries. Extract services later when scale demands it. This is not “quick.” This is how you avoid building a distributed disaster before you even have customers.

3. Security Considerations
Security is the product. Not a feature. Not a sprint-14 backlog item. The moment Infrastructure Copilot connects to ServiceNow, cloud platforms, logs, or enterprise knowledge bases, it becomes a sensitive operational control plane.
The internal Microsoft-Secure-AI--Technical-Guide-for-Architects says secure AI is an enterprise security architecture problem spanning identity, data governance, cloud posture, application security, policy enforcement, detection engineering, compliance, and operational resilience. It also states that AI systems should access only approved data, through trusted identities, within defined policy boundaries, with telemetry for monitoring, investigation, and response. [Microsoft...Architects | SharePoint]
Mandatory Security Controls
Identity and Access

SSO with Microsoft Entra ID, Okta, and SAML/OIDC
Tenant-level RBAC
User-level permissions
Service-account governance
Just-in-time admin access
SCIM provisioning for enterprise customers
MFA enforcement through customer IdP

Data Isolation

Every table must include tenant_id
Every API request must resolve tenant context
Every vector chunk must include tenant and access metadata
Every integration token must be tenant-scoped
No cross-tenant cache keys
No shared prompt context across tenants
No global embeddings without tenant boundary enforcement

AI Security
OWASP’s 2025 LLM Top 10 includes risks such as prompt injection, sensitive information disclosure, supply chain risk, data and model poisoning, improper output handling, excessive agency, system prompt leakage, vector and embedding weaknesses, misinformation, and unbounded consumption. These must map directly into our threat model. [owasp.org], [owasp.org]
For Infrastructure Copilot, that means:

Prompt injection detection
Retrieval filtering before model call
Output validation before tool execution
No autonomous production changes initially
Human approval for remediation actions
Tool permission scoping
AI response citations
Sensitive-data redaction
Full audit trail
Model usage monitoring
Token abuse controls

Critical principle: The model must never be trusted as an authority. It is an assistant behind policy, not a god with API keys. Revolutionary concept, apparently.

Support multiple tenancy models:

Microsoft guidance states that multitenancy does not imply every component is shared. It means at least some components are shared across tenants. That gives us room to design tiers: shared for smaller customers, isolated for large regulated customers. [learn.microsoft.com], [learn.microsoft.com]
B. AI Scalability
AI cost can destroy SaaS margins if uncontrolled.
Controls required:

Model gateway for routing requests
Token budget per tenant
Rate limits by plan
Cached answers for repeated queries
Batch embeddings
Background indexing
Hybrid retrieval to reduce unnecessary context
Smaller models for classification and routing
Larger models only for complex reasoning

5. Risks
Here is the brutal list.
Product Risks

Enterprises may already have ServiceNow AI, Azure Copilot, Dynatrace, Datadog, or Splunk AI.
“Infrastructure Copilot” sounds broad. Broad products are hard to sell.
If we try to support Azure, AWS, GCP, VMware, Kubernetes, ServiceNow, Jira, GitHub, Teams, and Slack from day one, we will build a graveyard of half-working connectors.

Technical Risks

Cross-tenant data leakage
Bad tenant isolation in vector search
Hallucinated remediation guidance
Prompt injection through tickets, logs, KB articles, or chat messages
Cloud API permission overreach
Integration rate limits
High AI inference cost
Poor retrieval quality
Weak auditability

Commercial Risks

Buyer may not trust AI to touch production operations.
Security approval cycles will be long.
If value is not measurable, procurement will kill it.
Competing against platform-native AI requires a sharper niche.

My challenge to your assumption
Do not position this as “Copilot for all infrastructure” at first. That is too wide.
Position v1 as:

AI-powered Incident and Change Intelligence for enterprise IT operations.

That wedge is closer to your real strength: MIM, ITSM, outages, change risk, RCA, communication. Win there first. Expand later.
