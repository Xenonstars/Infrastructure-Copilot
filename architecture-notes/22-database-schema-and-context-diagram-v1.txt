Infrastructure Copilot - Database Schema v1.0
1. Business Perspective
The database must support the business promise:

Reduce MTTR by connecting incidents, changes, alerts, assets, knowledge, runbooks, AI analysis, and audit history into one intelligence layer.

So the schema is not just “tables.” It must support:

Multi-tenant SaaS billing
MSP customer separation
Incident investigation
Change correlation
Knowledge ingestion
RAG citations
AI auditability
Security review readiness
Future cloud/infrastructure connectors

My challenge: do not store everything as JSON because “AI can understand it.” That is lazy architecture. Use relational tables for business-critical operational data, JSONB only for connector-specific payloads and flexible metadata.

3. Security Considerations
Non-Negotiable Rules

Every tenant-owned table must have tenant_id.
Every query must be tenant-scoped.
PostgreSQL RLS must be enabled on sensitive tenant tables.
Application role must not use database admin credentials.
AI interactions must be auditable.
RAG chunks must carry tenant and permission metadata.
Connector secrets must never be stored directly in PostgreSQL.
Store only Key Vault reference IDs for secrets.

Azure Database for PostgreSQL access guidance recommends using roles with least privilege and explicitly says not to use the administrator role for the application.  The internal Microsoft-Secure-AI--Technical-Guide-for-Architects references runtime safety, Prompt Shields, logging controls, connector governance, monitoring, audit readiness, and evidence preservation for enterprise AI workloads. [learn.microsoft.com] [Microsoft...Architects | SharePoint]
